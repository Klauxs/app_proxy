# Guard 事件唤醒与关闭准备优化：2026-09-20

## 实现

- ETW 回调在有界队列入队后通知发送循环，事件到达即发送，不再固定睡眠 100 ms 等下一轮。通知发生在等待前也会保留；回调不做刷新、文件写入或目标判断。
- 定时刷新改为 25 ms 固定时钟，错过周期采用 Skip；优先处理到期刷新，持续事件不能饿死会话归属和丢失计数检查。事件通知仅取队列，不额外刷新。保持断连退出、满批次排空及最后发送结束标记。
- 事件观测取得的程序文件、数据目录和进程句柄随任务传递，关闭准备复用这些句柄。仍核验配置 revision、实例绑定和当前安装登记，不跨事件缓存，也不删除精确进程身份检查。
- 事件任务不再单独落盘 Resolving、CheckingInstance 两个进度状态；在 Accepted 阶段完成准备，CheckingInstance 与停止 nonce/时间一起原子持久化。实例资源预留、停止意图和资源停止许可仍按原顺序落盘，然后才执行终止。取消、配置变更、一次性许可及崩溃恢复规则不变；恢复不会重放关闭。
- 仅用于重启的创建入口检查移至目标关闭后。普通启动及后台完整扫描流程保持原有状态推进。

## 回归

默认 workspace 初次 453 通过、1 失败、60 ignored。唯一失败来自旧心跳测试按“前次发送完成后睡眠”断言间隔，而新实现按固定时钟刷新；断言改为验证起始时钟到期后发送，监听 5 项测试通过，完整 Windows library 重跑 187 通过、0 失败、23 ignored。合计当前默认 **454 项通过、60 ignored**，不重复计算重跑项目。Clippy workspace/all-targets `-D warnings`、Release build、fmt 和 diff check 通过。

新/扩充覆盖：入队先于等待不丢通知；解码失败唤醒补扫；回调唤醒无需再次刷新；忙碌发送不饿死到期核验；合并进度状态后配置/取消仍阻止停止；停止意图写入失败原状态不产生许可；nonce 一次性及崩溃恢复不重放。证据 `.tools/guard-wakeup/workspace-tests.log`、`windows-regression.log`、`listener-tests.log`、`intent-test.log`、`test-summary.json`、`clippy.log`、`release-build.log`。

## 监听开销

在 active ETW 且测试实例未启动时，固定两进程句柄读取 GetProcessTimes，采样 15.000 秒。普通协调进程累计 CPU 时间增加 0.046875 秒，约占一个逻辑核的 0.3125%；提权监听进程累计计时未增加。后者受计时分辨率限制，不能解释为完全没有 CPU 开销。此为一次空闲采样，没有旧版本同时对照，也不代表事件风暴或高负载场景。证据 `.tools/guard-wakeup/cpu.json`、`cpu-ready.json`、`cpu.py`。

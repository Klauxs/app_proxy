# Claude 升级后旧容器占用的恢复

普通启动不扫描进程。MSIX 激活失败或超时后，只有本次调用时间范围内的 Windows AppModel-Runtime 208/215 事件同时证明容器共享冲突，才进入恢复。两个事件必须共享 ActivityID，且完整包名、应用 ID、AppProxy helper、当前用户 SID 和 `0x80070020` 均匹配。单独的 HRESULT、普通文件占用、历史事件、代理失败或无证据的超时都不会授权清理。

恢复目前仅覆盖 Claude。通过原生进程句柄读取完整包身份，筛选相同用户、相同会话、严格早于当前注册版本的 Claude 包进程。发现仍运行的旧版 `claude.exe` 就停止恢复。所有候选在结束前取得并保持精确的进程句柄，校验创建时间、用户、会话、镜像及包身份；不按 `git.exe` 等名称批量杀进程，也不遍历或终止父子进程树。当前版本、其他应用、其他用户/会话保持不动。

清理前再次核对包注册。恢复有 3 秒处理预算，权限不足或身份无法核验时明确失败，不自动提升权限。已识别但无权结束的进程不会转交给管理员监听器。仍可能存在无法读取的受保护进程，因此清理结果不能代替真正的启动回执。

调用方持有同一请求的一次性消费锁，只有 Pending 状态允许恢复。每个启动请求只恢复一次；完成后复用原请求重试一次，遵循原来的取消和过期规则。已消费/结果不明的请求不会重新创建应用。清理失败仍通过消费锁撤销来证明没有创建，不能根据错误码直接宣布未创建。

诊断写入该请求目录的 `recovery.json`，包括当前包、候选的进程身份、发出结束操作的 PID 和最终状态。记录不包含命令行、环境变量或代理凭据。普通日志/启动结果不代表网络请求已完成验证。

## 2026-09-23 现场验证

- 现场 Claude 为 `2.2553.13.0`，旧容器为 `2.2553.1.0`。唯一可见旧包进程是 PID 8544 的 Git fsmonitor 后台进程。
- 实际激活命令超时，但同次 Windows 208/215 事件确认共享冲突。Windows PowerShell 5 的 `Get-WinEvent` 时间筛选须传入本地 DateTime；传 UTC DateTime 会漏掉本次事件。
- 显式现场测试先复现冲突，再调用产品恢复实现，仅结束 PID 8544。重试包 helper 激活成功，旧版容器和旧版包进程计数均为 0，其他 5 个 Git 进程保留。
- 随后通过已安装 AppProxy 的现有实例启动真实 Claude，收到 confirmed 回执，PID 14588；命令行确认携带 `--proxy-server=http://127.0.0.1:57007`。
- 本次未测试 Claude 登录/聊天网络请求，也未将“新启动引擎完整自动恢复路径”冒充已经安装后的端到端验证。现场恢复调用的是新编译测试中的产品恢复函数，随后正常启动调用的是已有安装版本。
- 包相关回归 28 项通过、3 项默认忽略；启动引擎回归 43 项通过、1 项忽略；显式现场恢复测试 1 项通过；Windows/App 全目标 Clippy 警告为错误通过。

可重复的模拟回归涵盖 HRESULT 包装、不同活动/包/用户/helper/错误码事件的拒绝、严格旧版本筛选，以及繁忙/已消费/不匹配消费票据。现场恢复测试默认忽略，须显式提供 `APP_PROXY_RECOVERY_TEST_HOST`、`APP_PROXY_RECOVERY_TEST_LOG` 并单独运行 `recover_live_claude_container_conflict`；它会结束已确认旧包的残留进程，且要求真实冲突存在。
